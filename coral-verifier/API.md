# Coral verifier service: HTTP API v1

The contract between the Coral verifier service (HA add-on, owns the Coral USB, runs YOLOv9-s int8 512) and its clients (the Scrypted mixin plugin, optionally Home Assistant). Both sides are built against this file. Change it here first.

Principles: the service is a sidecar and never in the video path. It is stateless for clients except per-camera sessions that expire by themselves. Clients must fail open: if the service is down, slow or returns an error, the client behaves exactly as it does without the service.

## Transport and auth

HTTP/1.1, JSON bodies, UTF-8. Default port 8750, bound on all interfaces of the host network. The add-on option `token` is REQUIRED (the service refuses to start with an empty one): every request except `GET /v1/health` must carry `X-Verifier-Token: <token>`; it is checked BEFORE any body is read (401, connection closed). Request limits: bodies need a `Content-Length` (chunked is refused with 411), at most 2 MB (`413`), headers and body must each arrive within 5 s in total (slow clients are cut), at most 64 concurrent connections (extra ones get an immediate 503). Timestamps are unix milliseconds. Boxes are normalised `[x0, y0, x1, y1]` in 0..1 of the submitted frame.

## Endpoints

`GET /v1/health` returns `{ok, version, model:{name,input,coral:"ok|stalled|missing"}, coral_ms:{median,p95,last}, stages:{decode_ms|preprocess_ms|infer_ms|post_ms|queue_ms|total_ms: {median,p95}}, dropped_stale, resets, queue_depth, cameras_active, uptime_s}`. `coral_ms` is the invoke time (same as `infer_ms`), `stages` are percentiles over the last 200 frames, `dropped_stale` counts frames shed or dropped as stale since start. `ok` is false when the Coral is missing or stalled; the service keeps retrying in the background. In that case the response status is HTTP 503 (the body is the same JSON with `ok:false`): clients and the Supervisor watchdog treat a non-200 health as unhealthy. Health also reports `t_clamped`, the number of frames whose `t` was replaced by server time (see rule 10).

`POST /v1/cameras/{camera}/frame` with body = one JPEG (`Content-Type: image/jpeg`; JPEG ONLY: the body must start with FFD8 and its frame header is read BEFORE decoding, anything else or above the pixel cap, default 16 MP, is `400`; 640 px wide or more recommended), query `t=<unix_ms>` (capture time, default now), optional `tiles=auto|1|2|3` (default auto: width/height <= 2.2 is one pass; wider frames run HYBRID = the WHOLE frame letterboxed plus two overlapping 55 % half tiles, 3 Coral invokes per frame, whole-frame detections win over tile pieces: a tile detection is dropped when > 60 % of it lies inside a same-group whole-frame detection, or when it is taller than 25 % of the frame height and overlaps one (IoU > 0.3), and the inner-tile-edge rule below applies only to tile detections; merged with per-class NMS (IoU 0.5) plus the vehicle cross-class NMS; whole frame is still ONE request/queue slot, `infer_ms`/`coral_ms` are summed over the invokes; explicit `1` = whole frame only, `2` = the two 55 % tiles only, `3` = three evenly spread tiles with 30 % overlap and no whole pass; the whole frame is still ONE request/queue slot with several Coral invokes inside, `infer_ms`/`coral_ms` are summed over them. Constants: `defaults.TILING`), optional `deadline_ms=<n>` (> 0, otherwise 400; the longest this frame may wait in the service queue; older frames are dropped with `503 {reason:"stale"}`), optional `prio=normal|low` (default normal, otherwise 400; `low` marks background monitoring frames: when the queue is full the oldest LOW frame is shed first, and a low frame is only served when no normal frame is waiting, so it never delays a normal one), optional `verbose=1` (include detections below 0.2; by default replies omit them). The service letterboxes, runs the Coral, updates that camera's session and replies:

```
{
  "camera": "front_door",
  "t": 1791886000000,
  "coral_ms": 31.2, "queue_ms": 4.0,
  "decode_ms": 1.1, "preprocess_ms": 0.4, "infer_ms": 31.2, "post_ms": 0.6, "total_ms": 37.4,
  "detections": [{"cls": "person", "group": "person", "score": 0.83, "box": [0.1, 0.2, 0.3, 0.9]}, {"cls": "car", "group": "vehicle", ...}],
  "person":  {"state": "idle|candidate|confirmed|holding", "confirmed": true, "present": true,
              "since_ms": 1791885990000, "last_seen_ms": 1791886000000, "tracks": 1},
  "vehicle": {"moving": false, "tracks": [{"id": 3, "cls": "car", "state": "parked", "parked": true, "since_ms": 1791880000000}]},
  "animal":  {"present": true, "confirmed": true, "tracks": [{"id": 0, "cls": "dog", "since_ms": 1791885995000}]},
```

Detection classes and thresholds (internal constants in `verifier/defaults.py`, not add-on options). Every detection is `{cls, group, score, box}`, `group` = `person|vehicle|animal`. airplane, train, boat and elephant are never reported.

| group | classes | reported / tracked from | notes |
|---|---|---|---|
| person | person | camera `cont_thr` (default 0.2) | state machine below, unchanged |
| vehicle | bicycle, car, motorcycle, bus, truck | car, motorcycle, bus, truck 0.40, bicycle 0.5 (car, motorcycle, bus, truck also reported weak in [0.25, 0.40)) | tracking and parked logic below; a bicycle behaves exactly like a car: it makes `vehicle.moving` true while non-parked and `parked` after `parked_after_s` |
| animal | bird, cat, dog, horse, sheep, cow, bear | 0.3 (confirmation 0.6) | `animal` object below |

`animal`: an independent state machine with the person tick logic (same 1-second ticks and merge of frames < 0.75 s apart) on animal detections of any class: confirmed when a detection >= 0.6 is seen in 2 of 3 one-second ticks; kept alive while detections >= 0.3 matched to a track keep arriving; held 6 s after the last one (no stationary lock). `present` = `confirmed` = confirmed or holding (both fields carry the same value). `tracks` are simple IoU tracks (`id`, `cls`, `since_ms` = first seen) that live for the 6 s hold and exist only while `present`; there is no parked concept. Constants: `defaults.ANIMAL`. Multi-tile frames: a box within 2 % of the tile width of an INNER tile edge (not the frame border) whose extent lies entirely inside the neighbouring tile is dropped (the neighbour sees the object whole); boxes touching only the frame border are kept. After the tile merge, car/truck/bus/motorcycle go through one cross-class NMS (IoU 0.5, higher score wins and keeps its class) and a vehicle box with more than 70 % of its area inside a larger vehicle box is dropped. Bicycle and the other groups are not part of it. Weak vehicles: car, motorcycle, bus and truck detections with score in [0.25, 0.40) are listed in `detections` with `"weak": true` (group `vehicle`) for display only (bicycle has no weak band); strong ones (>= 0.40) carry no `weak` field. Weak vehicles never feed vehicle tracks, `parked`, `vehicle.moving` or any session state; per-class NMS ranks by score so a weak box cannot suppress a strong one. Animals never affect the person state or the vehicle object (separate trackers, enforced by tests). Reading `GET /v1/cameras/{camera}` includes `animal`.

Person state machine (per camera, internal defaults, overridable per camera): `idle` (no track), `candidate` (a detection >= `start_thr` seen but not yet confirmed), `confirmed` (>= `confirm_n` TICKS with a box >= `start_thr` inside `confirm_m` seconds; default 2 of 3, start_thr 0.65; a tick is one second of frame time, frames less than 0.75 s apart are the SAME tick and merge, best score wins), `holding` (confirmed, no box >= `cont_thr` this frame, still within `hold_s`; default 8 s). While confirmed or holding, boxes >= `cont_thr` (default 0.2) matched to an existing track (IoU or centre-distance gate) keep it alive. `present` = state is `confirmed` or `holding`. A track that has not matched for `hold_s` ends; a track whose box has IoU > 0.7 with its own box `still_s` seconds earlier (default 3 s, rolling, as in the 1 fps reference simulation) is a "stationary lock" and survives gaps up to `still_hold_s` (default 30 s). `max_hold_s` (default 600 s) is a service-side safety with no counterpart in the reference simulation: a track without a detection >= `start_thr` for that long ends. The person logic reproduces the reference simulation's simulation decision for decision at 1 fps (tests/test_tracker_diff.py), including its off-by-one: a track may still be re-matched when its gap was `hold_s` + 1 s. Vehicles: boxes of car/truck/bus/motorcycle >= 0.40 and bicycle >= 0.5; a track with IoU > 0.7 between consecutive frames for > `parked_after_s` (default 120 s) is `parked`; `vehicle.moving` is true when a non-parked vehicle track is present.

`POST /v1/cameras/{camera}/config` with any of `{start_thr, cont_thr, confirm_n, confirm_m, hold_s, still_s, still_hold_s, max_hold_s, parked_after_s, session_ttl_s, vehicle_thr, animal_start_thr, animal_cont_thr, zoom_out}` sets per-camera overrides (200 with the effective config). `vehicle_thr` (default 0.40, 0.1-0.95) is the strong floor of car/truck/bus/motorcycle (bicycle stays 0.5); the weak display band is [0.25, vehicle_thr) and exists only when `vehicle_thr` > 0.25. `animal_start_thr` (default 0.6) and `animal_cont_thr` (default 0.3, also the animal decode floor) must satisfy 0.05 <= cont <= start <= 0.95. Person keeps `start_thr`/`cont_thr`. `zoom_out` (default 0 = off, 0..0.6): when > 0 the frame job adds ONE extra Coral pass with the whole frame shrunk to (1 - zoom_out) of its size, centred on a grey (114) canvas of the original size and letterboxed as usual (helps large objects cut by the frame edge); its boxes are mapped back to the original frame's normalised coordinates (scale and offset undone, clamped to 0..1) and merged like whole-frame boxes (per-class NMS plus vehicle cross-class NMS, exempt from the inner-tile-edge rule); stage timings sum over passes, still one request/queue slot. These affect decoding floors, filtering and trackers of THAT camera only (the engine decodes each frame with that camera's floors). `GET` on the same path returns it.

`POST /v1/cameras/{camera}/reset` clears the session (call on a raw-motion rising edge when a fresh episode starts). `GET /v1/cameras/{camera}` returns the current session state without submitting a frame (same shape as the frame reply minus detections); hold and vehicle expiry advance with the SERVER clock measured from the last frame's receipt, so a state read after silence shows the expired state. `GET /v1/cameras` lists active sessions. Sessions with no frame for `session_ttl_s` (default 120) are dropped.

`GET /v1/metrics` (token required, `X-Verifier-Token`) is the performance page feed. It returns `{coral:{state, invoke_ms:{median,p95,last}, utilization_pct, invocations_per_s, resets}, stages:{decode_ms|preprocess_ms|infer_ms|post_ms|queue_ms|total_ms:{median,p95}}, load:{queue_depth, dropped_stale_total, dropped_stale_60s, rejected_429_60s, cameras_active, frames_60s}, host:{cpu_pct, load1, mem_used_pct}, process:{cpu_pct, rss_mb}, gpu:{available, busy_pct}, uptime_s}`. It always answers 200 (also while the Coral is stalled: read `coral.state`). `utilization_pct` is the share of the last 60 s (or of the uptime when shorter) the Coral spent in invokes; `invocations_per_s`, `dropped_stale_60s`, `rejected_429_60s` (rate limit and camera cap) and `frames_60s` (frames answered 200) are over the same window, kept in a per-second ring (no per-frame logging). `host.cpu_pct` is system-wide and `gpu.busy_pct` is 100 minus the rc6 residency share of the first `/sys/class/drm/card*/gt/gt0/rc6_residency_ms`; both, and `process.cpu_pct` (this service plus the Coral child, 100 = one core, may exceed 100), come from a background sampler that runs every 5 s, so they cover the last ~5 s and are null for the first one. `gpu.available` is false (and `busy_pct` null) when the sysfs file is unreadable, for instance inside a container. Any value that cannot be read is `null`; the endpoint never fails because of it.

## Contract rulings (v1, binding)

1. Frame times: frames for one camera may carry `t` in the past (a pre-roll burst) and `t` must be non-decreasing per camera; an out-of-order `t` is clamped to the last one. All session timing (`since_ms`, `hold_s`, `confirm_m`, `still_s`) uses frame time. Pre-roll must be sent SEQUENTIALLY (wait for each reply): a deep parallel burst makes its oldest frames stale by design.
2. Rate limit: a burst of up to 10 frames within 1 s per camera is accepted (pre-roll); the 429 limit of 4 fps per camera applies to the sustained rate (token bucket, 10 capacity, 4 per second refill).
3. `reset` takes effect before any later request on the same connection and never clears per-camera config overrides; it also clears vehicle tracks. Clients wait for the 200 before sending frames.
4. `person.confirmed` is true for the whole time the state is `confirmed` or `holding` (sticky for the episode, false in `idle` and `candidate`); `present` is the same today but is the field clients should use for "someone is there".
5. `GET /v1/cameras/{camera}` and `GET /v1/cameras/{camera}/config` for an unknown camera return 404 with `{}`; `POST .../config` and `POST .../frame` create it. A camera is known while it has a live session or a config override.
6. `GET /v1/health` never returns 401.
7. `vehicle.moving` is true only when a vehicle track is in state `moving`. Each track has `state` = `moving|still|parked` (`parked` bool kept for compatibility). A new track is `still` (unknown, NOT moving): it becomes `moving` when, against its box at least 2 s of frame time earlier, the centre moved more than 3 % of the normalised frame diagonal or the IoU fell below 0.7, and `parked` after `parked_after_s` (120 s) without such movement (IoU > 0.7 with its anchor). A car that stops returns to `still` 2 s after it last moved. A track that vanishes keeps its last state for up to `hold_s`. A parked car seen after a service restart is therefore never `moving`. Constants: `defaults.MOVE_*`.
8. `max_hold_s` (service) is the longest a person may be held WITHOUT a confident detection (>= `start_thr`); the plugin has its own "Max hold" measured from confirmation.
9. `GET /v1/cameras` returns `{"cameras":[{camera, t, person_state, present, vehicle_moving, frames, age_s}]}`. `POST .../reset` returns `{camera, reset:true, had_session}`. Vehicle `since_ms` is the time the track was first seen.
10. Frame time bound: `t` is trusted only inside [server now - 60 s, server now + 5 s] and must be finite; otherwise (also 0, negative, inf, nan) the server receive time is used and `t_clamped` in health is incremented. A single bad `t` can never freeze or poison a session. A `t` that is not a number at all is `400`.
11. At most 64 cameras are known at once (option `max_cameras`); a new camera name beyond that is `429 {"error":"too many cameras"}` on frame and config. Camera names match `[A-Za-z0-9_.-]{1,64}`. Idle config overrides are dropped after 7 days.
12. `GET /v1/metrics` requires the token (401 otherwise), always returns 200 with the shape above, never raises on unreadable `/proc` or `/sys` (those fields are `null`, `gpu.available` false), and its 60 s figures are cheap rolling counters, not logs. `GET /v1/health` keeps all its fields unchanged.

## Latency policy (v1, binding)

The service never builds a backlog: the shared queue is bounded (internal `max_queue_depth` 8; when full the OLDEST request is shed) and a frame whose age since REQUEST ARRIVAL (decode included) exceeds `max_queue_age_ms` (default 400) or its own `deadline_ms` when it reaches the Coral is dropped. Both answer `503 {"reason":"stale"}`: clients treat this as "skip this frame", NOT as an outage (the Coral is fine, `/v1/health` stays ok). Stage timings: `decode_ms` JPEG decode (optionally at a reduced size, add-on option `jpeg_reduce`, OFF by default), `preprocess_ms` crop + letterbox + RGB + quantisation, `infer_ms` set_tensor + invoke + get_tensor (summed over tiles), `post_ms` decode + NMS + tile merge, `queue_ms` wait before the worker, `total_ms` arrival through post (excludes the network and JSON encode). Replies are compact, TCP_NODELAY and keep-alive are on, nothing is logged per frame at info level.

## Errors and limits

`400` bad image / bad parameter (messages never contain internals), `401` bad token, `411` Content-Length required (chunked refused), `413` body larger than 2 MB, `429` too many frames from one camera (sustained 4 per second, burst 10, body `{retry_after_ms}`), `503` Coral unavailable (body `{coral:"stalled|missing"}`) or frame dropped as stale (body `{reason:"stale"}`, see Latency policy), `500` otherwise. Clients treat any non-200 or a request taking longer than 2 s as "service unavailable" and fail open. Frames are processed in order of ARRIVAL (measured when the request is received, before decoding) through one Coral queue shared by all cameras; the Coral is owned by a child process that the service kills and restarts when an invoke takes more than 2 s or fails; the service never lets a stalled Coral block the HTTP server.
